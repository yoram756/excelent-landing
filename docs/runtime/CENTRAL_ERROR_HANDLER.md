## הגנות ומגבלות

מזהה שמגיע מגוף בקשה חיצונית אינו סמכות לעדכון ליד. עדכון מחייב metadata שנוצר ב־Stop And Error בתהליך מוכר, התאמה ללוח הקמפיין וקריאה חוזרת המאמתת פריט פעיל ושדות סטטוס. הסרה, לקוח ושלב לקוח משלם מוגנים. במקרה שאין יעד בטוח נוצרת רשומת תקלה נפרדת.

בכפילות נשמרת קודם תשובת HTTP 200 עם מזהה הבקשה הקיים, ואז מבוצעת עצירה. פריט הליד התקין אינו נעצר בגלל בקשת replay. כשל חיפוש אצל ספק אינו ממשיך למסלול יצירת ליד.

התהליך המרכזי אינו מפנה לעצמו. מקורות לא מוכרים ודוגמת ה־Error Trigger הידנית נפסלים. הודעות שגיאה מצונזרות לפני שליחה, וקישור הרצה מתקבל רק בנתיב המדויק בשרת המוגדר. התראות מוצלחות מנוכות לפי מזהה הרצה למשך שבעה ימים בזיכרון התהליך. זה אינו מנגנון נעילה אטומי בין ריצות מקבילות. אין retry אוטומטי על שליחת מייל או יצירת התראה שעלול לשכפל כתיבה שתוצאתה לא ידועה.

נמצאו ותוקנו גם סוגריים רצופים בביטוי חיפוש הטלפון הישן של LP Signup, שפירוש הביטוי ב־n8n קטע. לאחר התיקון הרשמה אמיתית עם נתוני TEST וה־replay שלה עברו. שגיאת הבדיקה המקורית 49852 עצמה טופלה בהצלחה ב־49853.

## מקורות ושחזור

`config/error-handler.json` מחזיק מזהי תהליכים והפניות ל־Credentials קיימים, ללא סודות. מזהי הלוח והעמודות ותוויות הסטטוס מגיעים מקובץ הקמפיין. מקורות המימוש הם `error-handler.js`, `build-error-workflow.js` ו־`error-workflow-patch.js` תחת `src/services/funnel/`.

בנייה: `node src/services/funnel/build-error-workflow.js src/services/funnel/dist/central-error-handler.json`.

הוספת ההגנות ליצוא מקורי שלא כולל אותן: `node src/services/funnel/error-workflow-patch.js input.json output.json leadIntake` (או `lpSignup`, `whatsappEngine`). היצואים הפרטיים נשמרים מחוץ ל־Git. הבונה הראשי משמר את ההגנות אוטומטית במנוע refi. בעת יצירת עותק של תהליך עם מזהה חדש יש לעדכן גם את רשימת המקורות המורשים ולבנות מחדש את המטפל המרכזי. הדבקת צמתים אינה מחליפה הגדרות Workflow; יש לשמור את Error Workflow בהגדרות ולבצע יצוא חוזר לאימות.
